# 019 — Exposing the app on the LAN through nginx (amends P003 D13, ADR-015)

- Author: bao-security · 2026-10-13 · Status: DRAFT for PM/user (user decision: nginx open on the LAN, project servers
  on ports 4000–4050, BOARD D-8)
- Amends: P003 D13 (the app was "localhost only"); ADR-015 §compose (ports bound to 127.0.0.1).

## 1. What changes in the threat model

Until now the only attacker who could reach the app was a process or web page on the same machine (DNS rebinding,
CSRF). On the LAN, **every device on 192.168.2.0/24** can open a TCP connection to the app. The app is a
single-user tool: whoever holds a session can start container jobs (GPU, disk), read datasets/outputs, export
models, and change settings. The HF token stays write-only, but jobs that use it can be started. **A session is
therefore equivalent to control of the project on this machine.** Everything below aims to keep that equivalence
from widening.

## 2. Topology

```
LAN device ──TLS──> 192.168.2.178:4000  (nginx, the ONLY port published on the LAN)
                      ├── /            -> app (compose network, app:7870; no host port on the LAN)
                      └── /site/ (opt) -> static files served by nginx itself
host-only:  127.0.0.1:4001..4050  dev servers, app debug port: never reachable from the LAN
```

- **Bind the LAN IP, not 0.0.0.0**: `ports: ["192.168.2.178:4000:8443"]`. Docker publishes through its own iptables
  chain and **ignores UFW**. Binding to 0.0.0.0 would also expose the port on every other interface (docker
  bridges, VPN/tailscale, a second NIC). The IP comes from `.env.local` (`VLM_LAN_BIND`), validated as an IPv4
  address of this host, never `0.0.0.0`.
- Subnet allowlist inside nginx: `allow 192.168.2.0/24; deny all;` (configurable `VLM_LAN_ALLOW`, default = the
  bind IP's /24). Because docker ignores UFW, this line is the firewall. Optional and stronger (needs sudo,
  user/PM): a `DOCKER-USER` iptables rule with the same subnet.
- The app keeps listening only inside the compose network; its `127.0.0.1:${VLM_PORT}` publish stays for local use
  (now inside 4001–4050). The runner stays `network_mode: none`. Dev servers stay on loopback and are NOT proxied
  by nginx in 1.0: nginx runs on the compose bridge, not with `network_mode: host`. Host networking would let a
  compromised nginx reach every loopback service of this shared host (kafka, elastic…).
- nginx container: official image pinned by digest (vetted by security, entry in IMAGES.lock). Use the
  `nginx-unprivileged` variant or `--user` with a port ≥ 1024 inside (8443). Also `read_only`, `cap_drop: [ALL]`,
  `no-new-privileges`, tmpfs for `/tmp` + cache with a size, `server_tokens off`. The config is generated by
  install.sh from a template in the repo (reviewed); there is no runtime config from the app.

## 3. TLS (mandatory)

- install.sh creates a **local CA with X.509 Name Constraints** (permitted: `IP:192.168.2.178/32`,
  `DNS:edgexpert-9786`, `DNS:edgexpert-9786.local`, `DNS:localhost`, `IP:127.0.0.1/32`), then a server cert with
  those SANs (≤ 397 days). Users install **this CA** on their devices. Thanks to the name constraints, a leaked CA
  key cannot mint a valid cert for any other site on those devices: this is the main risk of a home-made CA,
  and the constraint removes it.
- Keys: `~/.config/ntc-training/tls/` 0700; `ca.key` 0600 is used only by install.sh and never mounted anywhere.
  `server.key` 0600 is mounted read-only into nginx only.
- TLS 1.2 + 1.3, modern ciphers (Mozilla "intermediate"), no session tickets, OCSP off (private CA).
- Port 4000 speaks only TLS; a plain-HTTP request on it gets `error_page 497 = 301 https://$host:4000$request_uri`.
  No second port is opened.
- HSTS: `max-age=31536000` without `includeSubDomains`/`preload`, sent only when the Host is a name (browsers ignore it
  for IPs).

## 4. Host / Origin / cookies (D13 updated)

- nginx: one `server` with an explicit `server_name` list (the IP, `edgexpert-9786`, `edgexpert-9786.local`). The
  `default_server` returns 444 for any other Host. This keeps the DNS-rebinding defence at the edge.
- App allowlist (`VLM_PUBLIC_ORIGINS`, validated list): exactly `https://192.168.2.178:4000`,
  `https://edgexpert-9786:4000`, `https://edgexpert-9786.local:4000`, plus the existing `http://127.0.0.1:<port>` for
  local use. Host and Origin are checked against the same list. WebSocket Origin as well.
- The app trusts `X-Forwarded-Proto/For` **only** from the nginx peer (compose network address), and never sets the
  scheme from a client header otherwise.
- Cookie: `__Host-vlm_session`, `Secure; HttpOnly; SameSite=Strict; Path=/` (no Domain). When reached over plain
  `127.0.0.1` locally, the cookie without `Secure` stays as today (a separate name, never shared with LAN sessions).
- Session lifetime: idle 12 h, absolute 7 days, then the token link is needed again. Restarting the app invalidates
  all sessions (as today). Add a "sign out every device" action that rotates the token.

## 5. Login: the token never travels in a URL

- Today `GET /?token=…` puts the secret in the URL. Behind nginx it would land in access logs, the browser history
  and possibly a `Referer`. Change: the printed link becomes `https://host:4000/#t=<token>`. The fragment is never
  sent to a server. A tiny same-origin page reads it, `POST /api/session` with the token in the body (Origin
  checked), and clears it with `history.replaceState`. `GET ?token=` stays accepted ONLY from 127.0.0.1 and is
  refused through nginx.
- Token: ≥ 256 bits (`token_urlsafe(32)` today: OK). Constant-time compare (as today).
- Rate limit: nginx `limit_req` on `/api/session` (5/min per IP, burst 5). The app keeps a global failure counter:
  after 20 failures in 10 min, refuse logins for 15 min and log a warning. With a 256-bit token brute force is not
  the risk; this is noise and DoS control.

## 6. Headers, sizes, WebSocket, logs (nginx)

- Headers: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` (+ CSP
  `frame-ancestors 'none'`), `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`,
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`. The app's own CSP (connect-src 'self' + wss of the same origin)
  is passed through, not replaced.
- Body size: `client_max_body_size 2m` by default (workflow files), `21m` only on `POST /api/uploads` (app limit 20 MB).
  `proxy_request_buffering off` on uploads, so nginx does not spool to disk. Timeouts: 60 s for HTTP, 1 h read
  timeout on the WebSocket location.
- WebSocket: `proxy_http_version 1.1`, `Upgrade`/`Connection` mapped; only on the app's WS path.
- Logs: custom `log_format` with `$uri` (never `$request_uri`/`$args`), no Cookie/Authorization header, status, bytes,
  timing, client IP. Error log at `warn`. Rotation via docker log limits (`max-size`, `max-file`).
- Every other path is proxied to the app, which applies its own auth. No directory listing, no `/nginx_status`.

## 7. Release gates (added to checklist F)

- `ss -ltnp`: only `192.168.2.178:4000` (nginx) is reachable from the LAN; nothing on 0.0.0.0 from the stack.
- From a LAN device: plain HTTP → 301 to HTTPS; wrong Host → connection closed; a request from outside the allowed
  subnet (if testable) → 403; `/?token=` via nginx → refused; the login fragment flow works.
- testssl.sh / `openssl s_client`: TLS 1.2+, cert SANs, CA name constraints present.
- nginx access log contains no token after a login (grep the token prefix).
- Headers present (curl -I).

## 8. Residual risks (to tell the user)

1. **Anyone with a session controls the project** (jobs, data, exports). On a shared office LAN, any device in the
   subnet can try to log in. The 256-bit token makes guessing impossible, but a leaked link (chat, screenshot,
   shoulder-surfing) gives full access until the token is rotated. There is no per-user account or per-user audit
   in 1.0.
2. **Users must install the local CA.** Until they do, browsers warn, and users who click through can be
   intercepted on a hostile LAN. Name constraints limit the damage if the CA key leaks, but the CA is still a
   trust anchor the user adds to their device.
3. **Docker ignores UFW.** Protection relies on binding the LAN IP and on nginx's subnet rule. A DOCKER-USER rule
   (sudo) is stronger and is the user's choice.
4. **Larger attack surface**: nginx itself (pinned, Dependabot docker updates, non-root, read-only), and the app's
   HTTP surface is now reachable by more clients. A future app bug is exploitable from the LAN, not only from this
   machine.
5. **Resource abuse by an authenticated client** (GPU, disk) is bounded by the existing locks, quotas and memguard,
   not by identity.
6. Dev servers on 4001–4050 stay loopback-only. Exposing any of them would need its own review.
